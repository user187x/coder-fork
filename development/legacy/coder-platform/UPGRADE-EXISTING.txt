===================================================================================================
 CODER PLATFORM - UPGRADING A CLUSTER THAT ALREADY RUNS CODER
 (hub-and-spoke on AWS EKS: Coder cluster = spoke, Keycloak on the hub cluster)
 Bundle: coder-platform-airgap-1.0.0-coder2.37.3
===================================================================================================

Use this guide when the Coder cluster ALREADY has: Coder, the CloudNativePG operator (with Coder's
database), Traefik with a Gateway and the Gateway API CRDs. Keycloak runs on the hub cluster. For an
empty cluster use INSTALL-HELM.txt or INSTALL-ARGOCD.txt instead.

What the upgrade does, in this order (every step checks before it changes anything):
  - finds out how the existing Coder is set up (./upgrade discover) and writes install.conf for you
  - checks everything that could go wrong and prints exactly what it will do (./upgrade plan)
  - proves your existing templates still build with the new Coder (./upgrade tfcheck)
  - backs up Coder's database and the objects it touches (./upgrade backup)
  - upgrades Coder itself to 2.37.3 in place, through its own Helm release or Argo CD Application
  - adds the platform (dashboard add-ons, banner, template) next to it, without touching Coder's
    settings, users, database, route, the CloudNativePG operator, Keycloak or the Gateway
  - confirms every user, owner, template and running workspace is still there

Downtime: Coder restarts once (about one minute). Running workspaces keep running and reconnect.
Coder's database is migrated during that restart; that cannot be undone except by restoring the
backup (see ROLLBACK at the end).


---------------------------------------------------------------------------------------------------
PART A - ON THE CONNECTED MACHINE: FILL THE GOLD DIRECTORY
---------------------------------------------------------------------------------------------------

 1. From  data/apps/argocd/coder/coder-platform/dist/  copy to the USB drive folder (e.g. coder-gold/):
        coder-platform-airgap-1.0.0-coder2.37.3.tar.gz
        coder-platform-airgap-1.0.0-coder2.37.3.tar.gz.sha256
        UPGRADE-EXISTING.txt                     (this file)
        INSTALL-HELM.txt, INSTALL-ARGOCD.txt     (for reference)

 2. Terraform providers. Coder builds workspaces with Terraform, and on an air-gapped cluster the
    providers come from a mirror inside the Coder image. The bundle's mirror holds:
        coder/coder 2.18.0   and   hashicorp/kubernetes 3.2.1
    If your EXISTING templates use other providers or versions (for example hashicorp/aws,
    hashicorp/random, or kubernetes 2.x), build the bundle with them added:
        EXTRA_PROVIDERS="hashicorp/aws:5.100.0 hashicorp/kubernetes:2.38.0" ./build-bundle
    Not sure? Go ahead without them: step 16 (./upgrade tfcheck) tells you exactly which ones are
    missing, before anything is changed, and you come back to this step with that list.

 3. You do NOT need to bring the CA certificate: ./upgrade discover takes the shared CA bundle from
    what Coder already trusts.


---------------------------------------------------------------------------------------------------
PART B - BEFORE YOU START (CHECKLIST)
---------------------------------------------------------------------------------------------------

 4. Confirm each item:

    [ ] A Linux (x86_64) bastion with bash, curl, tar, sha256sum and network access to both EKS API
        servers, the registry, and https://coder.<your domain>.
    [ ] kubectl contexts for both clusters, with admin rights, e.g.:
            aws eks update-kubeconfig --name <coder cluster> --alias coder-spoke
            aws eks update-kubeconfig --name <hub cluster>   --alias hub
    [ ] The registry. For Amazon ECR:
          - the AWS CLI on the bastion, with permission to push and to create repositories
            (ecr:GetAuthorizationToken, ecr:CreateRepository, ecr:DescribeRepositories, ecr:*Upload*,
            ecr:PutImage, ecr:BatchCheckLayerAvailability)
          - the Coder cluster's node IAM role can pull (AmazonEC2ContainerRegistryReadOnly), and the
            VPC has endpoints for ecr.api, ecr.dkr and S3
        For another registry (e.g. Harbor): the project exists, you have push credentials, and the
        nodes trust its certificate.
    [ ] An owner of the existing Coder can create an API token for you (Account > Tokens in Coder,
        or `coder tokens create --lifetime 168h`). You paste it in step 12.
    [ ] Keycloak's "coder" client on the hub already works for the existing Coder (nothing changes
        there).
    [ ] If Coder restricts sign-in by Keycloak group (CODER_OIDC_ALLOWED_GROUPS) or maps groups/roles:
        the group names in Coder's settings match Keycloak's CURRENT groups. After a Keycloak rename
        (e.g. KeycloakAdminGroup -> KeycloakGroup with child group Admin) Coder must name the group as
        the token carries it: with the client's Group Membership mapper "Full group path" ON that is
        /KeycloakGroup/Admin; with it OFF just Admin (which then matches EVERY group called Admin).
        The upgrade keeps Coder's settings exactly as they are; step 13 lists them and flags bare names,
        and General > Keycloak checks each group against the realm after the upgrade (step 22).
    [ ] A maintenance window of about 30 minutes (Coder restarts once, in step 19).


---------------------------------------------------------------------------------------------------
PART C - UNPACK, DISCOVER, CONFIGURE
---------------------------------------------------------------------------------------------------

 5. Copy the gold directory to the bastion and open a terminal in it:
        cd /path/to/coder-gold

 6. Check the bundle (must print "OK"), unpack it, check every file (must print nothing):
        sha256sum -c coder-platform-airgap-1.0.0-coder2.37.3.tar.gz.sha256
        tar -xzf coder-platform-airgap-1.0.0-coder2.37.3.tar.gz
        cd coder-platform-airgap-1.0.0-coder2.37.3
        sha256sum -c --quiet SHA256SUMS

 7. Point kubectl at the CODER cluster (the spoke):
        kubectl config use-context coder-spoke
        kubectl config current-context

 8. Discover the existing setup. Read-only; changes nothing in the cluster:
        ./upgrade discover
    It prints what it found (Coder version, how Coder is deployed, database, Keycloak, CA bundle,
    Traefik, Gateway, Gateway API CRDs, CloudNativePG, workspaces) and writes:
        install.conf    all settings, filled in from the cluster
        ca.crt          the shared CA bundle, taken from what Coder already trusts

 9. Edit install.conf. Only these lines need you:
        vi install.conf
        REGISTRY=<registry>/<path>       e.g. 123456789012.dkr.ecr.us-gov-west-1.amazonaws.com/coder-platform
                                              or harbor.corp.example.com/coder-platform
        REGISTRY_USERNAME=...            only for a registry with a login (NOT for ECR)
        ADMINS="..."                     optional: extra Keycloak users to make owners
                                         ("username:email username2:email2")
    and, if Coder or the platform is managed by Argo CD on the HUB:
        ARGOCD_CONTEXT=hub               the hub's kube context from step 4
        DEPLOY=argocd                    (discover sets this when Coder itself is in Argo CD)
    If Traefik is behind an AWS load balancer and DNS isn't switched over yet, you can also set
        CODER_ADDRESS=<load balancer DNS name or IP>    (used only by the checks)
    Leave everything else as discover wrote it.

10. Only if the REGISTRY's certificate comes from your private CA:
        export SSL_CERT_FILE=$PWD/ca.crt

11. Only for Amazon ECR: make sure the AWS CLI has credentials for the account and region of the
    registry (e.g. export AWS_PROFILE=... or assume the role you use):
        aws sts get-caller-identity

12. Store the owner's API token (from step 4). Asked once, typing hidden; stored in the Coder
    cluster as Secret coder-platform-automation and renewed automatically on every later run:
        ./upgrade token

13. Plan. Read-only. Prints every check and exactly what the upgrade will do:
        ./upgrade plan
    It must end with "Ready to upgrade". Fix every BLOCK line and run it again. Typical BLOCKs and
    what to do:
      - "CODER_HIDE_AI_TASKS / --hide-ai-tasks is set"   remove it from Coder's configuration first
      - "a template named ubuntu-vnc-desktop already exists"   set TEMPLATE_NAME=<other> in install.conf
      - "Coder's pod can't fetch <issuer>"   the spoke can't reach or doesn't trust Keycloak on the hub
      - "managed by an Argo CD this machine can't read"   set ARGOCD_CONTEXT (step 9)
      - "coder-banner is managed by Argo CD"   delete that Application without deleting its resources:
            kubectl --context hub -n argocd patch application <name> --type json \
              -p '[{"op":"remove","path":"/metadata/finalizers"}]'
            kubectl --context hub -n argocd delete application <name>
    WARN lines are information (e.g. arm64 nodes: the bundle keeps its pods on amd64 nodes).


---------------------------------------------------------------------------------------------------
PART D - UPGRADE (RUN IN THIS EXACT ORDER)
---------------------------------------------------------------------------------------------------

    Either run everything in one go (it stops at the first problem):
        ./upgrade all
    or the same steps one by one, as below (recommended the first time):

14. Push the images (about 4 GB). For ECR it logs in with the AWS CLI and creates the repositories.
    Then it starts a tiny test pod to prove the nodes can pull from the registry:
        ./upgrade images
    Ends with:  "OK     a node pulled <registry>/library/python:3.13-alpine"

15. (Re-run the plan now that the images are there; it adds the template check result.)
        ./upgrade plan

16. Check that every EXISTING template still initializes with the new Coder image (and, for
    comparison, with the current one). Nothing is changed:
        ./upgrade tfcheck
    Every template must be "OK" or "fails with the current image too". A BLOCK line means the new
    image lacks a Terraform provider the template needs: note the provider(s) in the message, go back
    to step 2 with EXTRA_PROVIDERS, and start again with the new bundle.

17. Back up Coder's database and the objects the upgrade touches (to ./backups/<date>/):
        ./upgrade backup
    Ends with the dump's size and "readable by pg_restore". Copy the ./backups folder somewhere safe.

18. (Nothing has changed in the cluster up to this point.)

19. Upgrade Coder itself. Asks for confirmation; Coder restarts once and migrates its database:
        ./upgrade coder
    Ends with:  "OK     Coder 2.37.3 is running"

20. Add the platform (Secrets, Traefik's rewrite-body plugin, the chart in attach mode):
        ./upgrade platform
    If Traefik is managed by Argo CD, this stops and prints Helm values for Traefik's Application:
    add them there, sync it, and run step 20 again.
    Ends with:  "OK    release coder-platform deployed"  (or "Application coder-platform: Synced, Healthy")

21. Verify everything, including that no user, owner, template or running workspace was lost:
        ./upgrade verify
    Ends with "All checks passed." and an OK line per user/template/running workspace.


---------------------------------------------------------------------------------------------------
PART E - AFTER THE UPGRADE
---------------------------------------------------------------------------------------------------

22. Open https://coder.<your domain>, sign in with Keycloak as usual. Check General (Announcement,
    Classification, Change Logo, Monitoring, Keycloak), Settings > Certificates, and create a
    workspace from the new template to confirm it starts.
    In General > Keycloak, use "Connect to Keycloak" once (a Keycloak admin login on the hub; the
    password isn't stored). It then checks Keycloak's side too: the "coder" client, its secret against
    the Secret Coder reads, and every group Coder's settings name (exists in the realm, sent in the
    token in the same form).

23. Keep install.conf, ca.crt and the backups/ folder. Later upgrades: unpack the next bundle, copy
    install.conf and ca.crt into it, and run  ./upgrade plan  then  ./upgrade all.


---------------------------------------------------------------------------------------------------
ROLLBACK (only if step 19 or later went wrong and you must return to the old Coder)
---------------------------------------------------------------------------------------------------

  Both sequences below were rehearsed on the test clusters (users, owners, templates and a running
  workspace came back as they were before the upgrade). Run them from the bundle directory.

  B=$(cat generated/last-backup)            # the backup ./upgrade backup made
  NS=<Coder's namespace, e.g. coder>
  CL=<CloudNativePG cluster: POSTGRES_NAME in install.conf, e.g. coder-db>

  A) Coder managed by a Helm release (discover said: "managed by Helm release ...")
    A1. Stop Coder:
          kubectl -n $NS scale deploy/coder --replicas=0
    A2. Put the old database back:
          P=$(kubectl -n $NS get cluster.postgresql.cnpg.io $CL -o jsonpath='{.status.currentPrimary}')
          kubectl -n $NS exec $P -c postgres -- psql -c 'DROP DATABASE app WITH (FORCE)' -c 'CREATE DATABASE app OWNER app'
          kubectl -n $NS exec -i $P -c postgres -- pg_restore -d app --no-owner --role=app < $B/coder-db-v*.dump
    A3. Put the old Coder back (the revision before the upgrade: helm -n $NS history coder):
          helm -n $NS rollback coder <revision> --wait
    A4. Start Coder:
          kubectl -n $NS scale deploy/coder --replicas=1

  B) Coder managed by Argo CD (discover said: "managed by Argo CD Application ..."; on the hub: --context hub)
    B1. Pause the Application's auto-sync, or Argo CD restarts Coder during the restore:
          kubectl --context hub -n argocd patch application coder --type merge \
            -p '{"spec":{"syncPolicy":{"automated":null}}}'
    B2. Stop Coder:
          kubectl -n $NS scale deploy/coder --replicas=0
    B3. Put the old database back: the three commands of A2.
    B4. Replace the Application with the saved one (old chart, old image, auto-sync back on):
          tools/jq '{apiVersion,kind,metadata:{name:.metadata.name,namespace:.metadata.namespace,
                    labels:.metadata.labels,annotations:.metadata.annotations,finalizers:.metadata.finalizers},spec}' \
            $B/coder-argocd-application.json | kubectl --context hub replace -f -
        Argo CD syncs the old Coder back (and its replica count). Wait until it is Synced/Healthy:
          kubectl --context hub -n argocd get application coder -w

  The platform add-ons can stay (they work with the older Coder too). To remove them:
    Helm:    helm -n $NS uninstall coder-platform
    Argo CD: kubectl --context hub -n argocd delete application coder-platform


---------------------------------------------------------------------------------------------------
IF SOMETHING GOES WRONG
---------------------------------------------------------------------------------------------------

  - Every step can be run again after fixing the cause.
  - ./install status          pods, the setup Job's log
  - generated/                 what discover found (coder-deployment.json, before.json, tfcheck logs)
  - docs/coder-breaking-changes.md   Coder's breaking changes between versions
  - AGENTS.md                  common failures explained
